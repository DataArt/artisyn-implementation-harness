# Web Portal — Overview

Implementation detail for the Web Portal container: a composition-only Nx project at `apps/web-portal` with no application source. `scripts/ci/portal-assemble.ts` copies both static builds into `apps/web-portal/dist/` and fails the build on anything a deploy must not ship. Mirrors `docs/Target Architecture (HLD)/v1/Containers/Web Portal.md`.

- `apps/web-portal/project.json` — `sourceRoot` is empty: this project has no source of its own. `implicitDependencies: ["web-explorer", "web-docs"]` is the Nx project-graph edge that `nx affected` reads to mark `web-portal` affected whenever either sibling changes. The `build` target's `dependsOn: ["web-explorer:build", "web-docs:build"]` is task ordering: both builds run first. Its `inputs` are `default`, `^default`, `{workspaceRoot}/scripts/ci/portal-assemble.ts` and the env `PORTAL_MAX_BYTES`; `outputs` is `{projectRoot}/dist`; the command is `tsx scripts/ci/portal-assemble.ts`.

## Assembly flow

`portal-assemble.ts` runs its steps in order and throws a descriptive error at the first failure, so the Nx target and CI fail before anything is uploaded.

| Step | Action                                                                                                                        | Fails when                                                                                                                            |
| ---- | ----------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 1    | Resolve the size limit: 900 MB (`900 × 1024 × 1024` bytes, NFR-17), or `PORTAL_MAX_BYTES`                                     | `PORTAL_MAX_BYTES` is set but not an integer from 1 to the 900 MB limit — the override may only tighten the gate                      |
| 2    | Guard the docs mount                                                                                                          | `apps/web-explorer/out/docs` exists: Web Explorer must not emit anything under `docs/`                                                |
| 3    | Empty `apps/web-portal/dist/`, copy `apps/web-explorer/out/` to its root and `apps/web-docs/.vitepress/dist/` to `dist/docs/` | —                                                                                                                                     |
| 4    | Assert entry points                                                                                                           | `index.html`, `404.html`, `.nojekyll` or `docs/index.html` is missing; the error lists every missing file                             |
| 5    | Assert both agent indexes, `agent-index.json` and `docs/agent-index.json`                                                     | A file is missing or does not parse; `entries` is not a non-empty array; an entry breaks the contract (message names the entry index) |
| 6    | Measure the published size (sum of file sizes under `dist/`)                                                                  | The size is above the limit                                                                                                           |

The contract check in step 5 matches the entry type `src/agent/tools.ts` reads: `path`, `url`, `title` and `text` are non-empty strings, `description` is a string (it may be empty), and `headings` is an array. Web Explorer's e2e suite serves the docs index from a fixture, so this step is the one check of the real cross-container data ([Web Explorer — Agent Interface](../Web%20Explorer/02.%20Agent%20Interface.md#agent-index-contract)).

On success it logs the asserted files, the published size and the limit. The current measured size is recorded in NFR-17 (`docs/Target Architecture (HLD)/v1/Non-Functional Concerns/Requirements.md`).

## Integration patterns

- `yarn nx run web-portal:build` runs the two dependency builds first (separate Nx tasks), then `portal-assemble.ts`.
- `.github/workflows/deploy-web.yml` (workflow `Deploy web`) runs on every push to `main`. Its `nx affected --target=build` uses as base the head SHA of the last successful `deploy-web.yml` push run on `main`, falling back to the push's `before` commit, so a site change from a replaced or failed run is built by the next one. When `web-portal` is affected, the build produces `apps/web-portal/dist`. A step then checks that `dist` exists. Only then do the Pages steps run. Otherwise the run ends with a notice and deploys nothing.
- `deploy-web.yml`'s `actions/upload-pages-artifact` step's `path` is `apps/web-portal/dist` — this composed tree, not either app's own output.
- Negative checks run the script directly, not through Nx, because an Nx run rebuilds `out/` first: `PORTAL_MAX_BYTES=1 yarn tsx scripts/ci/portal-assemble.ts` fails on size; `PORTAL_MAX_BYTES=abc` and `=2000000000` fail on the override.

## Key decisions

- `implicitDependencies` (graph edge) and `build.dependsOn` (task ordering) are both declared, deliberately not collapsed into one — they answer different questions (`nx affected`'s change detection vs. the task runner's order) even though they name the same two projects.
- The assemble script fails loudly (throws, non-zero exit) rather than warn and continue — a partial deploy to GitHub Pages is worse than a failed CI build.
- `PORTAL_MAX_BYTES` is a build input and may only lower the limit, so neither a cached result nor an override can open the NFR-17 gate.
- `apps/web-portal/dist/` is the sole artifact `deploy-web.yml` uploads.

## Recommendation

**Option D (both surfaces, one shared relation-data source) is the structural answer** — it is the only option that satisfies both EC3 and EC4 as literally, separately, and strictly required by Frame. Options B and C each fail one of the two hard requirements outright; Option A is disqualified on both.

Falsifiable: void if either (a) EC3/EC4 are reclassified as soft requirements later, or (b) sizing data (OQ-1 below) shows the doc tree is small enough that a single IDE-rendered Mermaid artifact is itself sufficient as a de facto "published" surface, collapsing the need for two renderers.

**Important qualifier — do not over-resolve this recommendation:**

- **VitePress-side (EC4): closer to settled.** The developer has indicated the same build-time script driving graph generation for the infra-footprint decision also drives VitePress-build-time rendering, aligning with Option D/C's build-time-generation approach.
- **IDE-side (EC3): genuinely open.** The developer explicitly stated "how to render early on IDE... still i dont know" — a live, unresolved question about the rendering mechanism, not a resolved preference. This recommendation does NOT pick a specific IDE rendering mechanism — carried forward as a named open question, not decided here.

**Refinement — the VitePress-side rendering mechanism** (from a later developer idea): the VitePress-side interactive graph (Option D's site half) can be implemented by shipping the same `.sqlite` file Decision 1 (storage format) recommends directly to the browser and querying it live via `sql.js` (the WASM build of SQLite, already named as a sub-option in Decision 1's Research) paired with a JS graph-rendering library for the visual layer — rather than requiring a separate build-time JSON emission step. This ties the "shared data source" more literally: it is the same `.sqlite` file, not a derived copy, satisfying the regenerability/single-source-of-truth property even more strongly. This resolves part of OQ-3 below by naming `sql.js` as a concrete candidate for "the new JS graph-rendering library," though the graph-_layout_ library itself (for rendering nodes/edges visually, as opposed to querying the data) is still a separate, unresolved choice.

In short: structurally D (both surfaces, shared data source) — but the "how" of the IDE half, and the final choice of graph-layout rendering library for the site half, are both explicitly unresolved and must not be treated as decided.

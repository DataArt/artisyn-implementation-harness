## Recommendation

**Recommended option: Option C — SQLite file, specifically via the `node:sqlite` sub-option** (not `better-sqlite3`, not `sql.js`, for the Node-side build/agent script).

This resolves the "avoid new dependency unless proven necessary" constraint on its own terms: `node:sqlite` is not a new dependency in the package.json/lockfile sense — it's built into Node itself, and this repo's `package.json` already requires Node ≥24, well past `node:sqlite`'s Node 22.5 floor. This is the decisive factor separating `node:sqlite` from `better-sqlite3`/`sql.js` for the authoring/build side: those two do introduce a new dependency (a native binary or a WASM runtime) that the "avoid new deps" resolution disfavors.

SQL query power itself is not the reason to pick this option — no known consumer needs joins or traversal (OQ-2 already resolved this). The recommendation rests on the schema-constraint guarantees (uniqueness and foreign-key enforcement) and the zero-new-dependency property, not query power. This is stated explicitly so the recommendation isn't read as rubber-stamping an unneeded feature.

Accepted as a tradeoff: binary-format opacity (no PR diffability) and `node:sqlite`'s experimental-API status. Both are accepted because the artifact is a derived build output, not hand-edited source, and because the experimental-API risk is scoped to one internal script, not a public contract.

Option B (flat JSON/YAML) is the strongest alternative and the fallback if this recommendation is falsified: it meets every evaluation criterion but pushes schema validation into hand-rolled build-script code that SQLite gives for free. Options D and E are weaker: D risks carrying two sources of truth (frontmatter vs. committed edges) unless strictly validated, and E pushes parsing logic into every consumer independently, with unresolved IDE-interaction latency.

Falsifiability: (1) if `node:sqlite`'s experimental API is found missing a needed capability, or has a breaking change, fall back to Option B — not to `better-sqlite3` — since the "avoid new dependency" bar should still govern the fallback; (2) if EC2's "deterministic" is found to require byte-for-byte stable regeneration and SQLite's on-disk format can't guarantee it, this favors Option B; (3) if a future decision surfaces a consumer needing real join/traversal power, this strengthens — not weakens — the case for Option C.

Cross-cutting note with Decision 4 (visualization surface): the same `.sqlite` file this decision recommends is not Node-only — it can also be queried directly in the browser via `sql.js` (the WASM build of SQLite, from this file's own Option C sub-options), paired with a JS graph-rendering library, for the VitePress-published graph page. This means the storage choice serves both environments (Node via `node:sqlite` for the build/agent script, browser via `sql.js` for the published site) from one artifact, without needing a separate JSON export solely for client-side rendering — see Decision 4's Evaluate for how this resolves part of its open question on the VitePress-side rendering library.

## Recommendation

**Recommend Option 3 — Option 2's tier-typed nodes and lifecycle-action edges, plus the derived mirror-edge layer.**

It is the smallest option that fully satisfies EC2's literal requirement and answers two of the Problem statement's three named relationship examples precisely: "which Story produced which doc" (Option 2's six graduation edges) and a mechanized version of "which HLD container an LLD section implements" (the `mirrors-consistent`/`mirrors-gap` edge).

It satisfies the regenerability EC more strongly than required: the mirror edge needs no frontmatter ID at all. It honors the Product tier's categorical separateness by keeping `Product` a first-class node type untouched by the mirror logic.

The added build complexity (diffing `HLD/<Version>/Containers/` against `LLD/<Name>/` folder names) is acceptable: bounded, already-enforced logic, stays within "no new always-on service" (a second step inside the same build/CI job, not a new service), and produces a capability `/where-we-are` can consume directly.

Option 4's section-level granularity is NOT recommended — not demanded by any Known EC, and Roadmap §5.9's caution against speculative indexing applies directly given Option 4's own highest build/maintenance cost and new staleness risk. Defer until a measured gap justifies it.

Falsifiable test: if after Option 3 ships, `/where-we-are` or `/dev context` still cannot answer "which HLD container does this LLD doc implement" without an additional grep/read pass, Option 3 has failed and Option 4's finer granularity should be revisited. Conversely, if no developer/agent query ever needs finer-than-doc-level resolution after a reasonable adoption period, Option 4 remains correctly out of scope.

## Recommendation

**Revised recommendation: reads required (Context Gathering/Research, unchanged from the original Option B) — AND writes now also required at Document/Publish, but tool-automated rather than manually authored.**

This revises the original recommendation after developer review. The original rejection of Option C (mandatory read+write) rested on two concerns: (1) it conflicts with Roadmap §5.9's caution against blanket-mandatory indexing ahead of measured need, and (2) reliability — if a human is relied on to manually author an ID/edge as a required step, an unavailable or broken graph tool could block `/dev document` or `/design publish` from completing, with no documented fallback.

Both concerns dissolve once the write is **tool-automated, not manually authored**: the same zero-dependency `.mjs` script (from Decision 3, infra footprint, and Decision 6, bootstrap impact — which already auto-assigns a frontmatter ID to any doc missing one) is invoked automatically as part of `/dev document` and `/design publish` themselves, assigning an ID if the doc doesn't have one yet and writing the corresponding graduation edge. This is not a manual step a developer or agent could forget, skip, or botch — it is the same deterministic, idempotent operation the script already performs at bootstrap, just triggered at a different point in the lifecycle. Because it can't fail due to human diligence (there is no human step to skip), the reliability objection to Option C no longer applies.

On Roadmap §5.9: by the time Evaluate reaches this decision, Frame's own Problem statement is itself the measured gap the Roadmap asks for — requiring the write at the exact moment content already graduates (the doc is already being touched by `/dev document`/`/design publish` regardless) is not speculative additional indexing; it is closing the loop on a capability this design has already justified end-to-end. Making the write automatic and mandatory at that specific moment is proportionate, not speculative.

**What stays the same:** reads remain required at Context Gathering/Research (unchanged from the original recommendation) — nothing here affects that half of the decision. The graceful-degradation EC is still satisfied: a doc that doesn't yet have an ID isn't a stale/broken state requiring developer intervention, because the automated write step assigns one as a side effect of the doc already graduating — there is no window where an untracked doc blocks anything.

**Original Option C (as literally scoped in Research) stays rejected as written** — that version assumed a human-authored mandatory step with no automation and no documented fallback, which is a different, fragile design. This revision is not "adopting Option C" — it is "automating Option B's write side so that making it required no longer carries Option C's original risk."

**Option D (new dedicated step) and Option E (CI-only) remain not needed**, for the same reasons as before: D's only advantage (isolating write risk from Document/Publish) isn't a problem anymore once the write is automated and non-blocking; E still doesn't deliver authoring-time discovery value, though it remains a viable later addition as a determinism backstop.

**Falsifiability:** this revised recommendation is wrong if the automated script itself proves unreliable in practice (e.g., fails often enough that `/dev document`/`/design publish` completion is genuinely blocked) — in that case, fall back to the original best-effort/optional-write version of Option B, with the automation treated as encouraged rather than load-bearing.

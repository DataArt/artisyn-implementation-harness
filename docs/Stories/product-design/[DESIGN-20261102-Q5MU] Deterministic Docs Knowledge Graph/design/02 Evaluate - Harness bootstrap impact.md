## Recommendation

**Revised recommendation: Option B+ — the bootstrap script runs once, proactively, as part of `/harness-bootstrap launch` itself (not lazily deferred to whenever a later lifecycle phase happens to invoke it), and in that same pass it (1) assigns a deterministic, collision-safe frontmatter ID to any existing doc that doesn't have one yet, and (2) builds the initial graph from the result.**

This revises the original recommendation after developer review, who pointed out that a one-time pass at launch — generating initial coverage immediately, then relying on Decision 5's lifecycle wiring to keep it current — is exactly the shape they want, and asked why Option D was disqualified given that intent.

The answer is that Option D (as literally scoped in Research) was rejected for three specific, addressable risks, not because "index existing docs at bootstrap" is inherently wrong:

1. **Unspecified collision-handling** — solved here by using a deterministic, collision-proof ID generation scheme (e.g. derived from a stable hash of the doc's path plus a uniqueness check against already-assigned IDs), not ad hoc assignment.
2. **No retry/partial-success model** — solved by making the pass idempotent: it only touches docs that don't already have an ID, so it's always safe to re-run, and a partial run simply leaves some docs unindexed until the next run (consistent with the graceful-degradation EC, not a violation of it).
3. **Bigger blast radius than bootstrap's current scope** — addressed by scoping the mutation to be additive-only: the pass inserts exactly one frontmatter field (the ID) and never touches doc content, structure, or any other field. This is a much narrower operation than the "scan+assign with unspecified logic" Research's Option D described, and it's trivially reviewable/reversible via a plain git diff.

With these three risks addressed, this revised option no longer carries the reasons Option D was rejected for. It is still consistent with Frame's "incremental, not mass-migration" constraint in spirit: nothing about doc structure, content, or authoring conventions changes — only a missing identity field gets filled in, which is the same category of operation EC1 already asks every doc to eventually have, just performed proactively rather than left entirely to future individual edits.

**UX decision, confirmed with the developer:** this pass runs **silently** as part of `launch` — no confirmation prompt, even though it writes to every doc in the tree the first time it runs. This is consistent with how other additive, reversible, low-risk steps in this harness proceed without an explicit approval gate.

**What stays the same from the original Option B:** the script is still the single zero-dependency `.mjs` module (no new deps, built on `node:sqlite`), still framed as "what the bootstrap package should contain whenever it's built," still fully robust to `docs/Harness/package/` not existing yet in this checkout. The only change is timing (proactive at launch, not lazily deferred) and scope (now includes safe ID-assignment, not just indexing of docs that already happen to have one).

**Option C stays conditional, Option D's literal scoping stays rejected** — this revision does not resurrect Option D as originally written (no collision-handling, no retry model, broader blast radius); it is a new, narrower design that achieves the same practical outcome the developer wants without those specific risks.

**Falsifiability:** this revision is wrong if (1) the deterministic ID scheme is found to produce collisions in practice despite the uniqueness check (would require redesigning the ID generator, not reverting to deferred-only indexing), or (2) the "silent, no confirmation" UX choice is found to surprise developers in practice (e.g., unexpected diffs appearing across many files with no warning) — in that case, fall back to the summary-then-confirm UX variant that was considered and declined here.
